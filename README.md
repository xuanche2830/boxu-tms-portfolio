# 泊序：项目物流协同原型

一个项目可能同时找几家货代，还会穿插 UPS、FedEx 等国际快递。项目同事、物流同事和外部伙伴把进度写进同一张表时，单号、备注和实际动作容易混在一起。想知道“哪票还没人接、谁在跟进、交付材料齐不齐”，往往还得逐个追问。

泊序是围绕这个问题做的本地演示原型：项目员工提出发运需求，企业分配运输委托，获授权的货代更新自己负责的票，企业再跟进签收、异常和凭证复核。每一步都能回到对应的项目和订单查看。

**当前版本是 v0.12。截图以及预置的企业、人员、订单均为合成资料；尚未在真实企业或货代业务中上线。**

## 打开后可以做什么

从**工作总览**看待接单、待发运、运输中、部分签收、全部签收和已关单的委托，优先处理异常。进入某个项目后，可以登记货物、起止地和期望到货日，并把一条需求分批交给不同伙伴。

货代在自己获授权的运输委托中接单、填写单号和发运信息。企业员工按运输单元签收、处理异常；需要交付资料时，企业提出待补要求，货代上传文件，员工留下复核结论。**上传凭证不会自动确认签收或改变运输状态。**

负责人还可以查看成员与授权、导出记录，并建立包含附件的便携备份。页面入口按日常跟进、业务资料和企业设置分层；账号能看到什么，最终由服务端授权决定。

## 在本机试一遍

演示版需要 **Windows 和 Python 3.12+**。首次安装依赖需要网络。仓库已包含编译好的前端页面，直接体验不需要安装 Node.js。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe scripts\serve.py --demo
```

在浏览器打开 `http://127.0.0.1:8769/collaboration`。首次启动会生成六种运输阶段的合成订单。页面顶部可以切换企业负责人、项目员工和货代人员，分别走一遍“提出需求 → 分配委托 → 货代更新 → 企业签收和复核”。练习结果保存在本地的 `data/demo/`，重启后仍在。

端口 8769 被占用时，加 `--port 8771`；想另开一套全新的演示资料，加 `--fresh-demo`，旧练习不会被覆盖。按 `Ctrl+C` 停止服务。

如果想从空白空间开始，另开终端运行：

```powershell
.\.venv\Scripts\python.exe scripts\serve.py --work
```

工作空间默认地址是 `http://127.0.0.1:8768/collaboration`，首次进入需设置负责人账号。它使用独立的 `data/work/`，与演示资料分开。服务只监听本机地址。不要把工作库、日志或附件提交到公开仓库。

修改前端时，才需要 Node.js 22+ 和 pnpm 10：在 `frontend/` 运行 `pnpm install --frozen-lockfile`、`pnpm build`，然后刷新协同服务的 `/collaboration` 页面。

## 做到了哪一步

已完成的主线包括项目与需求、分批委托、运输节点、按件签收、异常、账号授权、CSV/XLSX 导入复核、附件和空库备份恢复。前端使用 React、TypeScript、Vite；后端使用 FastAPI、SQLModel、Alembic。默认数据库为 SQLite，也曾在隔离环境中验证 PostgreSQL。附件保存在私有目录，下载会重新检查授权与文件摘要。

这仍是**本机试点原型**。飞书实时同步、UPS/FedEx 接口、OCR/AI 提取、自动邀请、自助找回密码、病毒扫描和公网多租户部署都还没有做。待补凭证目前是协作提醒，没有独立责任人和期限，也不会阻止关单。

本机发布版做过业务、导入、附件和演示隔离检查，也走过“负责人要求 → 货代上传 → 员工复核”的浏览器流程。检查的具体项目、结果和未验证范围在 [验证记录](docs/VALIDATION.md)。若要在本机重新运行检查：

```powershell
.\.venv\Scripts\python.exe scripts\check.py all
```

检查会使用随机本机端口和独立的合成数据库，结果保存在不提交的 `.test-runs/`。GitHub Actions 也会在 Windows 环境安装、构建并执行同一组检查。
